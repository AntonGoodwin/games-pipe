# Журнал решений: mines

Допущения, которые пайплайн принял сам, и решения человека поверх них.
Файл ведёт оркестратор; человек меняет решения командой `/game-decide`.

## D-001 Сколько мин на поле и выбирает ли их число игрок?

- Статус: допущение
- Допущение: Ровно 3 мины, игрок число не выбирает; params = {}
- Обоснование: В описании число мин не задано. Фиксированное значение упрощает правила, валидацию и тесты; 3 из 25 — типичное значение для Mines
- Источник: [[local-jira/GAME-002-mines-new-game|GAME-002]] · этап spec · [[runs/r-006-GAME-002/report|r-006-GAME-002]]

## D-003 Как rng превращается в расположение мин и когда расставляются мины?

- Статус: допущение
- Допущение: В start, 3 вызова rng: частичная тасовка Фишера — Йетса, j = i + floor(rᵢ × (25 − i)), мины — c[0..2]; action rng не использует
- Обоснование: Исход фиксируется до первого хода (честность, без подстройки под ходы игрока). Ровно 3 вызова дают детерминированное управление через fixedRng. После rng ничего не может упасть
- Источник: [[local-jira/GAME-002-mines-new-game|GAME-002]] · этап spec · [[runs/r-006-GAME-002/report|r-006-GAME-002]]

## D-004 Как считается множитель и какой house edge?

- Статус: допущение
- Допущение: M(k) = round2(0.98 × C(25,k)/C(22,k)), M(0) = 1 только для отображения; выплата = bet × M(k)
- Обоснование: Честный множитель для 3 мин с тем же 2 % house edge, что в «Монетке». Округление множителя до центов даёт однозначные числа на экране и в тестах
- Источник: [[local-jira/GAME-002-mines-new-game|GAME-002]] · этап spec · [[runs/r-006-GAME-002/report|r-006-GAME-002]]

## D-005 Можно ли забрать выигрыш до первой открытой клетки?

- Статус: допущение
- Допущение: Нет: cashout при k = 0 даёт INVALID_ACTION
- Обоснование: Иначе выплата была бы bet × 1 без риска или требовала отдельного правила; описание говорит о выигрыше, который появляется после безопасных клеток
- Источник: [[local-jira/GAME-002-mines-new-game|GAME-002]] · этап spec · [[runs/r-006-GAME-002/report|r-006-GAME-002]]

## D-006 Что происходит, когда открыты все безопасные клетки?

- Статус: допущение

- Обоснование: Больше ходить некуда; оставлять раунд открытым без возможных ходов, кроме cashout, бессмысленно
- Источник: [[local-jira/GAME-002-mines-new-game|GAME-002]] · этап spec · [[runs/r-006-GAME-002/report|r-006-GAME-002]]

## D-042 Как выполнить SC-20, если интерфейс должен реагировать на WALLET_UNAVAILABLE, а проверка границ запрещает подстроку «wallet» в коде игры?

- Статус: допущение
- Допущение: Интерфейс задаёт явный список ошибок, которые только показываются: BET_OUT_OF_LIMITS, INSUFFICIENT_FUNDS, INVALID_PARAMS, INVALID_ACTION, NETWORK_ERROR. После любой другой ошибки (ROUND_CLOSED, ROUND_NOT_FOUND, WALLET_UNAVAILABLE, INTERNAL_ERROR, ROUND_ALREADY_OPEN и других неизвестных кодов) он пересинхронизируется через sdk.open(). Для этого кода в ERROR_TEXT нет своего текста: показываются код и message, которые пришли от платформы.
- Обоснование: Спецификация (D-028) требует пересинхронизироваться при ROUND_CLOSED, ROUND_NOT_FOUND и WALLET_UNAVAILABLE, а «остальные коды, например INVALID_ACTION» только показывать. После ответа INTERNAL_ERROR или неизвестного кода экран тоже может не совпадать с сервером, поэтому повторный open() здесь безопаснее (KB-008). Все тесты SC-15 и SC-20 проходят. Проверка в factory/lib/checks.ts:141 (/wallet|:4001/i) слишком широкая: она срабатывает на коде ошибки платформы, хотя обращения к кошельку нет. Это дефект проверки для оркестратора. Её стоит ограничить настоящим доступом к кошельку, например вызовом fetch/XHR, URL с :4001 или заголовком x-wallet-token.
- Источник: [[local-jira/GAME-003-mines-feedback|GAME-003]] · этап implement · [[runs/r-007-GAME-003/report|r-007-GAME-003]]
