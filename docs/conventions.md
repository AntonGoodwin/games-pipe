# Конвенции проекта

Обязательны для всех агентов фабрики. Короткие правила; подробности — в [[platform/spec]] и [[platform/README]].

## Стек

- Node.js 24, TypeScript **без сборки**: Node запускает `.ts` напрямую (type stripping).
  - Только стираемый синтаксис: без `enum`, `namespace`, параметров-свойств в конструкторе (`constructor(private x)`).
  - Импорт типов — `import type`. Относительные импорты — с расширением `.ts`.
  - Проверка: `pnpm exec tsc --noEmit -p tsconfig.json`.
- HTTP — встроенный `node:http`, без фреймворков. Новые npm-зависимости не добавлять: `package.json` принадлежит фабрике.
- Тесты — vitest (`pnpm exec vitest run <путь>`). Для тестов интерфейса в браузерном окружении есть `happy-dom` (`// @vitest-environment happy-dom` в начале файла).
- Интерфейс игры — один `ui/index.html` с инлайновыми стилями и скриптом, без фреймворков и графических материалов. Подключает `/sdk.js` и работает только через `window.PlatformSDK`.

## Структура

```
platform/            общая часть (заморожена после создания)
  spec.md  README.md
  wallet/  core/  sdk/types.ts  sdk/client.js  testkit/index.ts  start.ts  tests/
games/<id>/
  manifest.json      { id, title, server, ui }
  spec.md            спецификация и сценарии SC-N
  README.md          документация кода
  server/index.ts    export default GameModule — механика и определение результата
  ui/index.html      интерфейс
  tests/*.test.ts    приёмочные тесты (пишет только агент тестирования)
decisions/<scope>.md журнал решений (ведёт оркестратор)
kb/                  база знаний (ведёт оркестратор по итогам ретроспективы)
local-jira/          задачи
```

## Границы игры и платформы

- Игра импортирует из платформы только `platform/sdk/*`. Ядро, кошелёк и другие игры — запрещено (проверяется кодом).
- Игра не знает о кошельке и балансе: ставку списывает и выплату зачисляет платформа по результату `Step`.
- Результат определяется на сервере в `GameModule` с использованием переданного `rng`. `Math.random` в игре запрещён.
- До завершения раунда `publicView` не раскрывает скрытое (например, расположение мин).

## Спецификации

- Коротко: одна мысль — один раздел, без пересказа платформы. Ссылки в стиле Obsidian: `[[platform/spec]]`, `[[decisions/<scope>#D-001]]`, `[[local-jira/GAME-001-...]]`. Путь — от корня репозитория, без `.md`.
- Сценарии приёмки — Gherkin, у каждого ID: `SC-1`, `SC-2` у игр, `PL-1` у платформы. Номер удалённого сценария не переиспользуется.
- В сценариях — конкретные числа: ставка, исход, ожидаемая выплата и баланс.
- Каждое допущение, которого нет во входном описании, — в поле `decisions` результата этапа. Оркестратор запишет его в журнал и присвоит номер.

## Тесты

- Приёмочные тесты пишутся по спецификации **до** реализации и проверяют поведение через `platform/testkit` (`createTestPlatform`, `fixedRng`), а не внутренности модуля.
- Каждый сценарий — минимум один тест, в названии ID: `it('SC-3: ставка вне лимитов отклоняется до списания', ...)`.
- Управляемый исход: `fixedRng([...])`. Тест должен ловить ошибку в правилах и выплатах: проверяй точные суммы выплат и баланс после раунда, а не «что-то изменилось».
- Тесты детерминированы: без реального времени, сети и случайности.
- Интерфейс: элементы для проверки помечаются `data-testid`, состояние — `data-state` (`idle | playing | won | lost | settled`).

## Документация кода

- `README.md` в каждой области: назначение, устройство, состояние раунда, как определяется результат, как запустить тесты; вики-ссылки на спеку, решения и платформу.
- TSDoc-комментарий (`/** ... */`) над каждым `export` в `.ts`-файлах (проверяется кодом).

## Отчёт этапа

Каждый этап заканчивается структурированным результатом (JSON по схеме): исход, краткое резюме, допущения, применённые записи базы знаний. Не пиши «готово», если не проверил: прогони тесты и `tsc` сам.
